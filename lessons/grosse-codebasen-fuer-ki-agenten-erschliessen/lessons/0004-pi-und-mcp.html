Kapitel 04 · Transfer und Troubleshooting

Read-only ins eigene Repository übertragen

Eine reale Navigationsfrage bearbeiten, Evidenz festhalten und den getrackten Git-Zustand vorher und nachher vergleichen.

15 Minutendeine Codebasekeine Dateiänderung

Dein Ergebnis

Du führst in deinem eigenen Repository einen vollständigen read-only Transfer von globaler Orientierung zu einer bestätigten Symbolbeziehung durch. Ein Evidenz-Arbeitsblatt trennt Tool-Befund, Gegenprüfung und offene Unsicherheit.

Die konkrete Aufgabe

Wähle einen Ablauf, den du grob kennst, dessen internen Einstieg du aber nicht auswendig weißt: zum Beispiel „Wo beginnt das Einlesen der Anwendungskonfiguration?“ oder „Welche Klasse nimmt eingehende HTTP-Anfragen für Bereich X an?“ Formuliere genau eine Ausgangsfrage. Gesucht werden Einstieg, eine nachgelagerte Symbolbeziehung und ein manuell bestätigter Beleg – kein Änderungsvorschlag.

Ausgangsfrage ↓ Repo-Map-Befund: plausible Pfade und Symbole ↓ konkrete Frage zu genau einem Symbol ↓ Serena-Beleg: Definition oder Referenz ↓ manuelle Gegenprüfung + offene Unsicherheit

Vorher: getrackten Zustand festhalten

Die Übung funktioniert auch in einem bereits bearbeiteten Repository. Der Vergleich verlangt nicht „clean“, sondern „vorher und nachher identisch“.

cd /pfad/zu/deinem/git-repository
git rev-parse --show-toplevel
git status --short

STATE_DIR="$(mktemp -d "${TMPDIR:-/tmp}/pi-read-only-state.XXXXXX")"
git status --short --untracked-files=no > "$STATE_DIR/tracked.before"
git diff --binary > "$STATE_DIR/unstaged.before.diff"
git diff --cached --binary > "$STATE_DIR/staged.before.diff"
printf 'Zustand gespeichert in %s\n' "$STATE_DIR"

Bewahre den ausgegebenen Pfad bis zum Abschluss auf. Die drei Dateien dokumentieren Status sowie unstaged und staged Änderungen der getrackten Dateien.

Repo Map als erster Zug

Starte Pi im Git-Root und ersetze <DEINE_AUSGANGSFRAGE>:

Untersuche read-only: <DEINE_AUSGANGSFRAGE>
Rufe zuerst repo_map mit map_tokens=2048 auf. Nenne ausschließlich
Pfade und Symbole, die in der Tool-Ausgabe sichtbar sind. Wähle daraus
ein Einstiegssymbol und formuliere eine konkrete Serena-Frage dazu.
Verändere keine Dateien.

Stoppe kurz nach dem Map-Aufruf. Übertrage höchstens drei plausible Kandidaten in das Arbeitsblatt. Was nicht in der Ausgabe steht, ist noch kein Map-Befund.

Mit Serena eine Beziehung prüfen

Lass Pi die zuvor formulierte Symbolfrage bearbeiten:

Arbeite weiter read-only und verwende ausschließlich Serena.
Finde das gewählte Symbol mit relativem Pfad und Symbolart. Prüfe danach
genau eine passende Referenz- oder Implementierungsbeziehung. Trenne
sichtbare Serena-Belege von deiner Interpretation und benenne eine
offene Unsicherheit. Verändere keine Dateien.

Öffne anschließend den Definitionspfad selbst in Editor oder IDE. Bestätige mindestens Symbolname und die eine behauptete Beziehung. Eine Textsuche darf als Gegenprüfung dienen; sie ersetzt die semantische Serena-Abfrage nicht.

Evidenz-Arbeitsblatt

Fülle dieses Arbeitsblatt während der Übung aus oder öffne die druckfreundliche Referenz.

Nachher: getrackten Zustand vergleichen

Beende Pi regulär. Verwende exakt den zuvor ausgegebenen Wert für STATE_DIR, falls du das Terminal gewechselt hast.

git status --short
git status --short --untracked-files=no > "$STATE_DIR/tracked.after"
git diff --binary > "$STATE_DIR/unstaged.after.diff"
git diff --cached --binary > "$STATE_DIR/staged.after.diff"

cmp "$STATE_DIR/tracked.before" "$STATE_DIR/tracked.after"
cmp "$STATE_DIR/unstaged.before.diff" "$STATE_DIR/unstaged.after.diff"
cmp "$STATE_DIR/staged.before.diff" "$STATE_DIR/staged.after.diff"

Bestanden: Alle drei cmp-Aufrufe bleiben ohne Ausgabe und enden mit Exit-Code 0. Der getrackte Zustand ist damit vorher und nachher identisch. Prüfe die sichtbare Ausgabe von git status --short zusätzlich auf unerwartete ungetrackte Artefakte.

Wenn ein Schritt fehlschlägt

  1. Analyse: Fehlermeldung und letzten belegten Zustand notieren.
  2. Hypothese: genau eine plausible Ursache priorisieren.
  3. Nächster Befehl: einen engeren Check ausführen, der nur diese Ursache prüft.

Wiederhole keinen fehlgeschlagenen Aufruf unverändert.
