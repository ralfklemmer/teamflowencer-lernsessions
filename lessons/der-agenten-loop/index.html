Der Agenten-Loop

10 Stationen · etwa 12 Minuten

Ein Ablauf statt Prompts

Software entsteht hier in einem sicheren Prozess, Station für Station wie auf einer Linie: Grillen, Spec, Tickets, Umsetzen, Review. Jeden Schritt startest du selbst per Slash-Befehl, der Agent ruft ihn nie von allein auf. Jeder Durchlauf verbessert das Projektwissen.

Schritt: eine Station der Linie. Ein Schritt kann eine oder mehrere Chat-Sessions dauern.
Projektwissen: Glossar, Entscheidungen (ADRs) und Anweisungen wie CLAUDE.md bzw. AGENTS.md. Der Agent liest es bei jedem Lauf.

Der Agent hat letzte Woche einen Fachbegriff falsch benutzt. Was sorgt dafür, dass er es heute richtig macht?

Prompts sind Wegwerfware. Was im Repo steht, liest der Agent jedes Mal.

Der Agent fragt dich aus

Beim Grillen fragt dich der Agent zu deinem Plan aus, in Runden. Jede Frage bringt seine Empfehlung mit, du sagst ja oder entscheidest anders. Deine Antworten erzeugen die Fragen der nächsten Runde. Was schon im Code steht, schaut er selbst nach. Fertig ist es, wenn nichts mehr offen ist.

Grillen: Befehl /grilling, oder /grill-with-docs, wenn dabei Dateien entstehen sollen (nächste Station).

Der Agent will wissen, welche Datenbank euer Projekt heute schon nutzt. Fragt er dich?

Was im Code steht, sucht er selbst. Dich fragt er nur, was noch zu entscheiden ist.

Was landet in Dateien?

/grill-with-docs grillt und schreibt dabei Dateien. Fachbegriffe landen sofort im Glossar. Entscheidungen laufen durch einen Filter mit drei Stufen: schwer rückgängig zu machen, ohne Kontext überraschend, eine echte Abwägung. Nur was alle drei passiert, wird eine eigene Datei, ein ADR. Der Rest steht nur im Chat und ist nach /clear weg, wenn du ihn nicht vorher sicherst.

ADR: Architecture Decision Record, eine kurze Notiz zu einer Entscheidung und ihrem Warum.
/clear: leert den Chat komplett. Mehr dazu in Station 9.
Bauweise: /grill-with-docs = /grilling + /domain-modeling.

Beim Grillen eurer Web-App entscheidet ihr zwei Dinge: die Farbe der Buttons und Postgres statt SQLite als Datenbank. Welche Entscheidung wird ein ADR?

Eine Farbe änderst du in einer Minute, eine Datenbank nicht. Die Button-Farbe bleibt im Chat, bis du sie mit /to-spec sicherst.

Abzweigen, nicht anhalten

Manches willst du nicht beschreiben, sondern sehen und ausprobieren: Wie fühlt sich der Ablauf an, trägt das Datenmodell? Dafür brauchst du laufenden Code. Du schickst genau diese Frage in eine zweite Session, lässt dort einen Prototyp bauen und arbeitest selbst weiter.

/handoff: schreibt den Stand in eine Datei. Die zweite Session (eigenes Terminal, eigener Ordner) liest sie.
/prototype: baut Code zum Anschauen und Ausprobieren, der genau eine Frage beantwortet. Die Antwort bringst du in deine Session zurück.

Was passiert mit dem Prototyp-Code?

Ein Prototyp macht eine Unbekannte billig sichtbar, mehr nicht.

Entscheidungen festhalten

/to-spec schreibt die Entscheidungen auf, die ihr beim Grillen schon getroffen habt, als eine Spec. Neues entscheidet es nicht, und es stellt keine neuen Fragen. Einzige Rückfrage vorher: An welcher Test-Schnittstelle wird getestet? Lohnt sich, wenn die Arbeit nicht in eine Session passt.

Test-Schnittstelle (englisch Seam): die öffentliche Stelle, an der ein Test das Verhalten von außen prüft. Ideal ist eine einzige, möglichst weit außen.
Tracker: GitHub-Issues oder Markdown-Dateien im Repo, festgelegt per /setup-matt-pocock-skills.

Ein Feature braucht geschätzt drei Sessions. Was kommt nach dem Grillen?

Bleib dafür im selben Chat: Die Spec braucht den ganzen Gesprächsverlauf.

Vertikal schneiden

/to-tickets zerlegt die Spec in Tickets. Jedes Ticket ist ein vertikaler Schnitt durch alle technischen Schichten. Die Tickets werden nacheinander erledigt und geschlossen. Die Spec bleibt als Referenz, bis das ganze Feature fertig ist, danach kann sie weg.

Ticket: eine Scheibe, die für sich testbar ist und in eine frische Session passt. Es liegt im selben Tracker wie die Spec.

Welches Ticket ist gut?

Nur ein Durchstich lässt sich allein vorführen und prüfen.

Ein Ticket umsetzen

/implement nimmt ein Ticket, arbeitet testgetrieben, prüft sich am Ende selbst und committet. In einer Sandbox läuft das auch, während du weg bist.

Test-Stil: Tests prüfen Verhalten nur über die öffentliche Schnittstelle und lesen sich wie eine Spezifikation, also eher BDD/ATDD als kleinteilige Unit-Tests. Der Rhythmus bleibt rot, dann grün, ein Test pro Runde. Refactoring kommt erst im Review.
AFK: away from keyboard. Der Agent arbeitet, während du etwas anderes tust.
Sandbox: abgeschotteter Ort, z. B. ein Docker-Container, aus dem nur Commits herauskommen. Werkzeug dafür: Sandcastle.

Wo setzt der Agent beim Umsetzen seine Tests an?

Die Test-Schnittstelle hast du bei /to-spec bestätigt. Tests gegen Interna brechen bei jedem Umbau.

Aus Fehlern lernen

Am Ende von /implement läuft /code-review: zwei Prüfer parallel, einer gegen eure Coding-Regeln, einer gegen Ticket und Spec. Du liest den Bericht und ziehst Konsequenzen: Du reparierst den Code, und was der Agent künftig wissen muss, legst du im Projektwissen fest. Neue Fachbegriffe ins Glossar, neue Entscheidungen als ADR, neue Arbeitsregeln in CLAUDE.md bzw. AGENTS.md. Selbst oder per Auftrag an den Agenten.

Vermeidbarer Fehler: einer, der nur passiert, weil dem Agenten Wissen fehlte, etwa ein Fachbegriff oder eine Arbeitsregel.
Coding-Regeln: was euer Repo dazu dokumentiert, z. B. CONTRIBUTING.md, plus eine feste Liste typischer Code-Smells.
Diff: alle Änderungen seit einem Fixpunkt, z. B. seit main. /code-review kannst du auch selbst starten, etwa für einen ganzen Branch.

Der Agent nannte Kunden „User“, euer Fachbegriff ist „Mandant“. Wohin gehört der Fix dauerhaft?

Ein Fachbegriff ist Wissen, das jeder künftige Lauf braucht. Der Bericht schlägt nur vor, entscheiden tust du.

Zwischen zwei Schritten: Chat aufräumen

Ist ein Schritt der Linie fertig, etwa das Grillen, ist das Kontextfenster des Chats voll mit dem Verlauf. Das ist ein Problem: Mit vollem Fenster arbeitet der Agent ungenauer, und irgendwann ist kein Platz mehr. Drei Wege weiter:

  • /compact verdichtet den Verlauf, du arbeitest hier weiter.
  • /clear leert alles. Gut, wenn das Wichtige schon in Dateien steht.
  • /handoff packt die Arbeit in eine Datei für einen anderen Ort.
Kontextfenster: alles, was der Agent gerade gleichzeitig im Blick hat. Es ist begrenzt.
/compact, /clear: eingebaute Befehle, die Namen stammen aus Claude Code. Entsprechungen je Agent:
Agentverdichtenfrisch starten
Claude Code/compact/clear
Codex CLI/compact/new oder /clear
Pi/compact/new
/handoff: kennst du aus Station 4. Es macht Arbeit transportierbar: für einen Abzweig, ein anderes Tool, einen anderen Ordner oder einen Kollegen.

Du willst die Arbeit morgen in Codex statt in Claude Code fortsetzen. Was nimmst du?

Codex sieht deinen Claude-Chat nicht. Nur eine Datei kommt dort an. Lies sie, bevor du sie weitergibst.

Spickzettel: Welcher Befehl jetzt?

Für die Praxis nach dem Kurs: Wähle, wo du gerade stehst, und du siehst, welche Befehle du der Reihe nach eintippst.
